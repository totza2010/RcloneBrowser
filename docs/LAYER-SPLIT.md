> เขียน 2026-08-25 · ทำต่อจาก [`QUEUE-MOVE.md`](QUEUE-MOVE.md) และ [`SCHEDULER-MOVE.md`](SCHEDULER-MOVE.md)

## "แยกขาด" แปลว่าอะไรกันแน่

ไม่ใช่ "ไม่มี violation" — ตอนนี้ก็ไม่มีอยู่แล้ว `rbcore` ลิงก์แค่ Core, Network, Sql
ไม่มี Widgets **linker เป็นคนบังคับ ไม่ใช่คนรีวิว** และ `scripts/check_layers.py` ผ่านมาตลอด

เกณฑ์ที่ใช้ในเอกสารนี้แคบกว่านั้น และวัดได้:

> **ทุกการตัดสินใจต้องมีบ้านอยู่นอกหน้าต่าง**
> หน้าต่างเหลือแค่สองหน้าที่: วาดสิ่งที่ core บอก และส่งสิ่งที่ผู้ใช้กดเข้าไปให้ core
>
> ข้อพิสูจน์คือ **ถามคำถามนั้นโดยไม่มีหน้าต่างแล้วต้องได้คำตอบ**

## กฎที่ใช้ตลอด — มาจากบทเรียนสองรอบก่อน

1. **นับก่อนลงมือ** ตอนย้ายคิวเดา 20 ของจริง 118 ตอนย้าย scheduler นับได้ 149
2. **ทำตัวกลางก่อน แล้วตัดทีละตัว** อย่าเปลี่ยนทั้งก้อน
3. **ระวังสองคนขับพร้อมกัน** — `setDrivesItself` มีไว้เพราะเรื่องนี้
4. **แก้ซอร์สด้วย `Edit` หรือ Python ที่ `assert`** ห้าม PowerShell เขียนไฟล์
5. **ฆ่าโปรแกรมก่อนบิ้ว** เช็ค `EXIT` กับ `LastWriteTime` ก่อนให้คนทดสอบ
6. **วางเครื่องวัดก่อนผ่าตัด** — ใส่ log ก่อนย้าย จะได้เทียบก่อน-หลังได้

## ข้อ 6 คือหัวใจของรอบนี้

ทุกบล็อกต้องเพิ่มบรรทัด log ที่**พิสูจน์ว่าใครเป็นคนตัดสินใจ** เพราะเกณฑ์รับงานของรอบนี้
ไม่ใช่ "คอมไพล์ผ่าน" แต่คือ **อ่าน log แล้วเห็นว่า core เป็นคนตอบ ไม่ใช่หน้าต่าง**

หมวดใหม่ที่จะเพิ่ม: `rb.script` · `rb.remote` · `rb.task`

ตารางทดสอบ [`VERIFY.md` V-24](VERIFY.md) จึงมีคอลัมน์ **"บรรทัดที่ต้องเห็นใน log"**
ทุกแถว — ถ้าไม่มีบรรทัดนั้น แปลว่ายังไม่ได้ย้าย ต่อให้โปรแกรมทำงานถูกก็ตาม

## บล็อก 1 เสร็จแล้ว — และวิธีทำงานนี้จับของตัวเองได้ทันที

`ScriptRunner` (L1) ฟัง `JobQueue::emptied` และ `JobRegistry` เอง ตัด 4 จุดใน
`main_window` ทิ้ง หมวด log ใหม่ `rb.script` → `logs/scripts/scripts.txt`

**ผ่าน build ผ่าน test 18 ชุด แต่ข้อ 1.7 ไม่ผ่าน** — งานรันจบ exit 0 แต่ไม่มีบรรทัด
`rb.script` เลยสักบรรทัด สองสาเหตุซ้อนกัน:

1. `ScriptRunner::install()` ถูกเรียกจาก `MainWindow` เท่านั้น
2. **`TaskRunner` ไม่ได้เดินผ่าน `JobRegistry`** — มันรัน rclone เองด้วย `QProcess`
   ของตัวเอง สัญญาณ `jobStarted`/`jobFinished` จึงไม่เคยเกิดในโหมดไม่มีหน้าต่าง

นี่คืออาการ **"แยกครึ่งเดียว"** ที่เอกสารนี้เตือนไว้ในหัวข้อข้างบนเอง — ย้ายความสามารถ
เข้า core แล้ว แต่**การต่อสาย**ยังผูกกับหน้าต่าง

แก้โดยให้ `TaskRunner` เรียก `ScriptRunner::run(..., waitForIt=true)` ที่จุดเริ่มและจุดจบ
`waitForIt` จำเป็นเพราะ process กำลังจะจบ — script ที่ไม่รอ คือ script ที่ถูกฆ่าทันที

> **ข้อค้นพบที่ยังไม่ได้แก้:** `TaskRunner` ไม่เดินผ่าน `JobRegistry` แปลว่างานที่สั่งจาก
> command line ไม่มี job card ไม่มี stats ไม่มีทางหยุดจากที่อื่น และเขียนประวัติเอง
> คนละทางกับงานในหน้าต่าง **สมควรเป็นบล็อกของตัวเอง** ก่อนทำ S11 เพราะ API
> จะต้องสั่งงานแล้วเห็นงานนั้นเหมือนกับที่หน้าต่างเห็น

## บล็อก 2 เสร็จแล้ว

`RemoteRegistry::refresh()` **มีอยู่แล้วตั้งแต่ S5** ครบทั้งการรัน การอ่าน และการแยก

## บล็อก 4 เสร็จแล้ว

การ**อ่านข้อมูล** เป็น core อยู่แล้วตั้งแต่ S6 (`LsjsonParser`) ที่ยังติดอยู่ใน GUI คือ
**การไปถาม** — `ItemModel::load()` รัน `rclone lsjson` เอง สลับกับการสร้างแถวในต้นไม้
ตัวหมุน spinner และการนับ process ที่วิ่งอยู่

`DirectoryListing` แยกเฉพาะส่วนนั้น: ถาม → ทยอยส่ง entries → จบ หรือ ล้มเหลว
`QProcess` ใน `item_model.cpp` เหลือ **0**

**แก้บั๊กเงียบไปหนึ่งตัว** โค้ดเดิมต่อสัญญาณแค่ `QProcess::finished` แต่ **process ที่
start ไม่ติดจะไม่มีวัน finished** แถว `... loading` จึงหมุนค้างตลอดกาล ตอนนี้
`failed` ล้างแถวเหมือนกัน

**และเจอ null dereference ที่รอวันเกิด** — `errorOccurred` ยิงก่อนแล้วเคลียร์ process ทิ้ง
ถ้า Qt ส่ง `finished()` ตามมา การอ่าน stderr จาก pointer นั้นคือ crash
บนเครื่องนี้ Qt ไม่ส่ง แต่นั่นคือการพึ่งพฤติกรรมที่ไม่ได้รับประกัน

**GUI-free 68/111 → 70/113**

## แผน: บอกว่าทำไมเปิดโฟลเดอร์ไม่ได้

**ปัญหา** ตอนนี้โฟลเดอร์ที่อ่านไม่ได้แสดงเป็น**รายการว่าง** ซึ่งอ่านได้ว่า
"ไม่มีอะไรอยู่ในนี้" ทั้งที่ความจริงคือ "อ่านไม่ได้" — เหตุผลมีอยู่แล้วใน
`DirectoryListing::failed` และใน log แต่ไม่เคยไปถึงหน้าจอ

จากการทดสอบ 2026-08-26 เหตุผลจริงสองแบบที่เจอ ต่างกันมาก:

| ข้อความจาก rclone | ความหมาย | ควรบอกให้ทำอะไร |
|---|---|---|
| `The process cannot access the file because it is being used by another process` | **ชั่วคราว** — config ถูกล็อกอยู่ | ลองใหม่ |
| `didn't find section in config file ("...")` | **ถาวร** — remote นั้นไม่มีแล้ว | ไปตั้งค่า remote |

บนจอทั้งสองแบบหน้าตาเหมือนกันเป๊ะ

**ที่คิดไว้**

1. **แถวบอกเหตุผล** แทนที่แถว `... loading` ที่หายไป ใช้ `Item::Special` ที่มีอยู่แล้ว
   — โครงสร้างรองรับอยู่แล้ว เพราะแถว loading ก็ใช้ทางนี้
2. **ตัดหัวข้อความของ rclone ทิ้ง** — `2026/08/26 14:36:48 CRITICAL: ` ไม่ได้บอกอะไร
   กับคนอ่าน และข้อความจริงมักยาวหลายบรรทัด ควรเอาบรรทัดแรกที่มีเนื้อ
3. **แยกชั่วคราว/ถาวร** ถ้าทำได้ ให้แถวชั่วคราวกดเพื่อลองใหม่ได้
4. **ไม่เด้ง dialog** การกางโฟลเดอร์เป็นการกระทำเบาๆ และการโหลดล่วงหน้าหนึ่งชั้น
   จะทำให้เด้งหลายกล่องพร้อมกัน — ที่ทำให้เห็นต้องอยู่ในที่ที่มันเกิด

**ขนาดงาน** เล็ก (~30 บรรทัด) เพราะสัญญาณ `failed` เดินมาถึงโมเดลแล้ว
ที่เหลือคือเลือกว่าจะแสดงยังไง

## บล็อก 5 เสร็จแล้ว

### สิ่งที่เจอ ใหญ่กว่าที่วางแผนไว้ — regex เดียวกัน เขียนไว้ 9 ที่

`check_dialog` · `dedupe_dialog` · `mount_dialog` · `remote_folder_dialog` ·
`job_options` · `script_runner` · `main_window` ×2 · `utils`

**และแตกเป็นสองสำนวนแล้ว** — 3 ที่ใช้ `(?:"..."...)` อีก 6 ที่ใช้ `("..."...)`

นี่คือกฎว่า `--exclude "My Films"` แปลว่าอะไร **เก้าสำเนาคือเก้าโอกาสที่บรรทัดเดียวกัน

ที่รันไว้ตอนเช้าวันเดียวกัน — **ตรงกันทุกตัวอักษร**

### check · dedupe · export เดินผ่าน `JobRegistry` แล้ว

เมื่อก่อนสร้าง `QProcess` ดิบส่งให้ `ProgressDialog` รัน ผลคือ **ไม่มีประวัติ ไม่มีไฟล์ log
หยุดจากที่อื่นไม่ได้ และ API สั่งไม่ได้**

ตอนนี้เป็นงานจริง มี `JobKind::Check` · `Dedupe` · `Export`

**ไม่มีการ์ดในแท็บ Jobs** โดยตั้งใจ — `addJobCard` กรอง `JobKind::Transfer` อยู่แล้ว
งานพวกนี้แสดง output ในหน้าต่างที่สั่งมันเหมือนเดิม การเข้า registry มีไว้เพื่อ
**ประวัติ ไฟล์ log และทางเดินเดียวในการสั่ง rclone** ไม่ใช่เพื่อให้ถูกวาดสองที่

`ProgressDialog` รับได้ทั้ง `QProcess` (ของเดิม 7 ที่ ยังไม่แตะ) และ `RunningJob` (ของใหม่)

**ข้อควรรู้:** `RunningJob::start()` เติม `GetRcloneConf()` ต่อท้ายเอง ของเดิมใส่ไว้หน้าสุด

## AppCore — สิ่งสุดท้ายที่กั้นอยู่ระหว่างตอนนั้นกับ daemon

ทุกส่วนตอบได้เองโดยไม่ต้องมีหน้าต่างแล้ว **แต่ไม่มีใครประกอบมันเข้าด้วยกันนอกจาก
constructor ของ `MainWindow`** — อ่านคิว อ่านตารางเวลา ติดตั้ง `ScriptRunner`
ถือนาฬิกา ทั้งหมดอยู่ในนั้น บิลด์ที่ไม่มีหน้าต่างจึงมีชิ้นส่วนครบแต่ไม่มีสายไฟ

เป็นอาการเดียวกับที่ `ScriptRunner` เจอ แต่สูงขึ้นมาหนึ่งชั้น

`AppCore::start()` ทำห้าอย่าง ตามลำดับที่สำคัญ:

```
1. อ่าน path ของ rclone        ← ต้องมาก่อน เพราะข้อ 5 อาจเริ่มงานทันที
2. ติดตั้ง ScriptRunner        ← ต้องฟังอยู่ก่อนที่งานแรกจะเริ่ม
3. setDrivesItself(true)
4. โหลดตารางเวลา
5. โหลดคิว  → advance() → อาจเริ่มงานหัวคิวเลย
```

`MainWindow` กลายเป็น**ผู้ชม** — `watchAppCore()` ฟัง `ticked` · `scheduleFired` ·
`scheduleHeld` แล้ววาดตาม ไม่ยิงงานเอง

**และปุ่ม Run ก็เดินเส้นเดียวกัน** ตอนแรกผมย้ายแค่นาฬิกา ทำให้ปุ่มยังมีสำเนาของตัวเอง
60 บรรทัดในหน้าต่าง ซึ่งเป็น "สองวิธีสั่งให้ตารางทำงาน" — มากไปหนึ่ง ไม่ว่าอันไหนถูกวันนี้
ตอนนี้ทั้งคู่เรียก `AppCore::runNow()` ต่างกันแค่การรายงานผล (นาฬิกา → การ์ด,
ปุ่ม → กล่องข้อความ เพราะคนที่เพิ่งกดปุ่มควรได้คำตอบ)

**บรรทัด log ที่หน้าต่างยังเขียนเอง 11 → 5** และทั้งห้าเป็นการรายงาน ไม่ใช่การตัดสินใจ

`--daemon` เพิ่มมา 15 บรรทัดเพื่อพิสูจน์ข้อ 6.4 เท่านั้น ยังไม่มี HTTP ยังไม่มีวิธีสั่งหยุด

**GUI-free 70/113 → 72/115**

## `TaskRunner` เดินผ่าน `JobRegistry` แล้ว

พบตั้งแต่ตอนทำบล็อก 1 ว่า `--run-task` รัน rclone เอง เขียนประวัติเอง — **สองวิธีรัน task
โดยวิธีที่สองคือวิธีที่ไม่มีใครนั่งดู** ผลคือไม่มี stats หยุดจากที่อื่นไม่ได้ ไม่มีไฟล์ log
และคิวมองไม่เห็น

ตอนนี้เรียก `JobRegistry::start()` แล้วรอ `finished` ใน event loop
**ได้ไฟล์ log กับ remote control มาฟรี** ซึ่งของเดิมไม่มีเลย

**ที่ต้องระวังคือ exit code** ของเดิมแยก 69 (rclone เริ่มไม่ได้) กับ 70 (ไม่ได้จบปกติ)
ออกจาก exit code ของ rclone เอง พอเดินผ่าน `RunningJob` ทั้งสามอย่างมาทางเดียวกันหมด
จึงเพิ่ม `everStarted()` กับ `crashed()` ใน `RunningJob` และเช็คว่าไฟล์ rclone มีอยู่จริง
**ก่อน**เริ่ม — เพราะ "path ผิด" กับ "การถ่ายโอนล้มเหลว" เป็นคนละเรื่องกันสำหรับสคริปต์ที่อ่าน exit code

## `delete` ไม่ย้าย — และนี่เป็นการตัดสินใจ ไม่ใช่การมองข้าม

`DeleteProgressDialog` รัน **หนึ่ง process ต่อหนึ่งไฟล์** ขนานกันเป็นชุดๆ
(`deleteProcessor()` ปล่อยตามโควตา `rcloneLsProcessCount`)

ถ้าให้เดินผ่าน `JobRegistry` การลบ 500 ไฟล์จะได้ **500 แถวประวัติกับ 500 ไฟล์ log**
ประวัติเก็บได้ 2,000 แถว — การลบครั้งเดียวจะดันทุกอย่างที่เหลือตกขอบ

**การลบไม่เข้ากับรูปแบบ "งาน" ตามที่เขียนไว้ตอนนี้** ถ้าจะทำให้มีประวัติจริง ต้องเปลี่ยนเป็น
งานเดียวต่อการลบหนึ่งครั้ง (เช่น เขียนรายการลงไฟล์แล้วใช้ `--files-from`)
ซึ่งเป็นการเปลี่ยนพฤติกรรม ไม่ใช่การย้ายชั้น — เก็บไว้เป็นงานของตัวเอง
