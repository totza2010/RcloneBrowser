# เอกสารของโปรเจกต์

เอกสารทั้งห้านี้แบ่งหน้าที่กันชัดเจน ไม่เขียนเรื่องเดียวกันซ้ำ:

| ไฟล์ | ตอบคำถามว่า | อัปเดตเมื่อ |
|---|---|---|
| [`PLAN.md`](PLAN.md) | **จะทำอะไรต่อ และทำไม** — แผนทั้งหมด สถานะรายข้อ สิ่งที่ตัดทิ้งพร้อมเหตุผล | ปิดงานตามแผนได้หนึ่งข้อ |
| [`ARCHITECTURE.md`](ARCHITECTURE.md) | **โค้ดแบ่งชั้นอย่างไร** — ทะเบียนไฟล์ L0–L3 กฎที่ห้ามละเมิด จุดที่ยังละเมิดอยู่ | ย้ายไฟล์เข้า `rbcore` หรือเจอ `CORE:` / `LAYER:` marker ใหม่ |
| [`VERIFY.md`](VERIFY.md) | **ทดสอบแล้วหรือยัง** — V-01 ถึง V-16 พร้อมช่องให้ผู้ทดสอบกรอก PASS/FAIL | เพิ่ม `TEST:` marker ในโค้ด หรือมีคนทดสอบเสร็จ |
| [`QUEUE-MOVE.md`](QUEUE-MOVE.md) | **ผังการย้ายคิวเข้า `JobQueue`** — 12 บล็อก 118 จุด และลำดับที่จะตัด | ทิ้งได้เมื่อย้ายเสร็จ |
| [`DEV-SETUP.md`](DEV-SETUP.md) | **จะเริ่มแก้โค้ดได้อย่างไร** — เครื่องมือที่ต้องมี คำสั่ง build/test ประจำวัน | เปลี่ยน Qt เปลี่ยน toolchain หรือเพิ่มขั้นตอนใน workflow |
| [`API.md`](API.md) | **ระบบมีอะไรบ้าง และ API ควรหน้าตาแบบไหน** — สำรวจจากโค้ดจริงว่าแต่ละระบบเก็บอะไร สั่งอะไรได้ เพิ่มลบอย่างไร | เพิ่ม/แก้ระบบใดระบบหนึ่ง หรือคืบหน้าไปทาง E3 |

`docker/README.md` แยกอยู่ต่างหากเพราะเป็นคู่มือใช้งาน image ไม่ใช่เอกสารพัฒนา

## กฎการเขียน

**สถานะอยู่ที่เดียว** — `PLAN.md` บอกว่าข้อไหนเสร็จ `VERIFY.md` บอกว่าทดสอบผ่านหรือยัง
ทั้งสองอย่างไม่เหมือนกัน: โค้ดที่เขียนเสร็จและ CI เขียว ยังไม่ใช่โค้ดที่มีคนลองใช้แล้ว

**เขียนสิ่งที่วัดมา ไม่ใช่สิ่งที่คิดว่าจริง** — ตัวเลขในเอกสารเหล่านี้มาจากการรันจริงทั้งหมด
ถ้าประเมินไว้แล้วของจริงไม่ตรง ให้เขียนทั้งสองค่าไว้ (ดู §6.4 ใน `PLAN.md` เป็นตัวอย่าง)
เพราะที่ประเมินพลาดมักมีประโยชน์กว่าที่ประเมินถูก

**อย่าลบรายการที่ล้มเหลว** — ทางที่ลองแล้วไปไม่รอดให้บันทึกไว้พร้อมเหตุผล
มิฉะนั้นอีกหกเดือนจะมีคนมาลองใหม่ (ดู V-16 ที่บันทึกว่าอ่าน repo จาก binary ไม่ได้เพราะอะไร)
