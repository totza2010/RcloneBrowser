# แผนย้ายคิวเข้า `JobQueue` — ผังของสิ่งที่ต้องแตะ

> เขียน 2026-08-10 · ประกอบกับ [`API.md` §12 S3](API.md)
> ใช้ครั้งเดียวแล้วทิ้งได้เมื่อย้ายเสร็จ

## ทำไมต้องมีเอกสารนี้

ครั้งแรกที่ลองย้าย ประเมินว่า "ราว 20 จุด" **ของจริงคือ 118 จุด** และแต่ละจุดไม่ใช่การเปลี่ยนชื่อตัวแปร
แต่เป็นการเขียนบล็อกใหม่ เพราะในบล็อกเดียวกันมีทั้ง**การตัดสินใจ**และ**การวาด**ปนกัน

รายการข้างล่างไม่ได้มาจากการอ่านโค้ดเอาเอง — มาจากการลบตัวแปรสามตัวออกจาก `main_window.h`
แล้วให้คอมไพเลอร์ชี้ **จึงไม่มีทางตกหล่น**

## สามตัวแปรที่เป็นคิวตัวจริงในตอนนี้

| ตัวแปร | ความหมาย | ใน `JobQueue` |
|---|---|---|
| `mQueueStatus` | คิวเดินอยู่หรือหยุดพัก | `isRunning()` / `start()` / `pause()` |
| `mQueueCount` | มีกี่งานในคิว | `count()` |
| `mQueueTaskRunning` | หัวคิวกำลังวิ่งอยู่ไหม | `taskIsRunning()` |

ส่วน**ลำดับคิว**ไม่มีตัวแปรเลย — มันคือลำดับแถวใน `ui.queueListWidget` ซึ่งคือหัวใจของปัญหา

## ลำดับที่จะทำ

### ขั้น 0 — ตัดสินให้ได้ก่อนว่า "ใครขับ"

**ลองขั้น 1 ไปแล้วเมื่อ 2026-08-10 แล้วเจอกับดักนี้ จึงถอยกลับ**

ตัวกลางเองใช้ได้จริง — ใส่แล้ว **คอมไพล์ผ่านทันทีโดยไม่ต้องแก้สักจุดใน 118 จุด**
แต่พอ `JobQueue` ถูกสร้างขึ้นมาจริง มันต่อกับ `JobRegistry` ทันที แปลว่าตอนงานจบ
**มีสองคนสั่งเริ่มงานถัดไป** คิวเก่าในหน้าต่างกับคิวใหม่ ใครเร็วกว่าชนะ อีกคนอาจเริ่มซ้ำ

ทางแก้ที่ลอง: สวิตช์ `JobQueue::setDrivesItself(bool)` ปิดไว้จนกว่าหน้าต่างจะเลิกขับ
**ผลคือ `test_job_queue` แดง 3 เคส** โดยเคสแรกที่พังคือ `anEntryWhoseTaskIsGoneDoesNotStopTheQueue`
ค้างจนหมดเวลา ส่วนอีกสองเคสนับจำนวนเกิน (ได้ 4 ทั้งที่ควรได้ 3) ซึ่งเป็นผลต่อเนื่อง
จากงานที่ยังค้างอยู่ทำให้ `clear()` ไม่ล้างแถวที่กำลังวิ่ง

**สมมติฐานแรกที่ต้องตรวจ:** การแก้ไฟล์เทสต์ให้เรียก `setDrivesItself(true)` อาจไม่ได้ผลจริง
(สคริปต์แทนที่ข้อความไม่ได้ยืนยันว่าแทนสำเร็จ) ถ้าเป็นอย่างนั้น สวิตช์ยังปิดอยู่ในเทสต์
คิวจึงไม่เดินต่อ — เป็นความผิดของการแก้เทสต์ ไม่ใช่ของตัวสวิตช์

**ตรวจตามลำดับนี้:**

1. ยืนยันว่าเทสต์เรียก `setDrivesItself(true)` จริง (อ่านไฟล์หลังแก้ ไม่ใช่เชื่อสคริปต์)
2. ถ้าเรียกแล้วยังพัง แปลว่ามี state ค้างข้ามเทสต์จริง → เป็นบั๊กของ `clear()` / `load()`
   ที่ต้องแก้ก่อน และเป็นบั๊กที่มีอยู่แล้ววันนี้ ไม่ใช่ของใหม่
3. ทำให้ "ใครขับ" สลับได้อย่างสะอาด พร้อมเทสต์ที่พิสูจน์ว่าปิดแล้วไม่มีใครเริ่มงานเอง

**ห้ามไปขั้น 1 ก่อนข้อ 3 ผ่าน** — ถ้าสองคนขับพร้อมกัน อาการคืองานเดียวถูกเริ่มสองครั้ง
ซึ่งกับ transfer จริงแปลว่าเขียนปลายทางพร้อมกันสองโปรเซส

### สิ่งที่รู้จากการลองขั้น 1 รอบสอง (2026-08-10)

ใส่ตัวกลางแล้วทดสอบกับของจริง เจอสองอาการ **ทั้งคู่มาจากสาเหตุเดียว**

| อาการ | |
|---|---|
| งานสุดท้ายจบแล้วแท็บค้างที่ `Queue (1)>>(1)` | หน้าต่างเอาแถวออกแล้วเขียนตัวเลขทันที **ก่อน**บอกคิวว่าแถวหายไป · แก้โดยแทรก `saveQueueFile()` หลังการเอาแถวออกทั้ง **14 จุด** |
| ลบ 1 รายการแล้วเลขที่ลดคือตัว "กำลังทำ" ไม่ใช่ "รอ" | `mQueueTaskRunning` อ่านจาก `JobQueue::taskIsRunning()` ซึ่ง**เป็นจริงได้เฉพาะเมื่อ `JobQueue` เป็นคนสั่งเริ่มเอง** · ตอนนี้หน้าต่างเป็นคนสั่ง มันจึงตอบ "ไม่มี" เสมอ |

**ยืนยันแล้วว่าโค้ดเดิมไม่ได้ผิด** — ถอดตัวกลางออกแล้วทดสอบซ้ำ พฤติกรรมปกติทุกอย่าง
ในโค้ดเดิม สีเขียวของแถวกับ `mQueueTaskRunning` ถูกตั้งในบล็อกเดียวกัน จึงตรงกันเสมอ
ตัวกลางคือสิ่งที่ทำให้สองอย่างนี้แยกจากกันได้

**ทางแก้ที่ลองแล้วยังไม่ได้ผล:** ให้ `JobQueue::syncRunningFromRegistry()` ดูจาก
`JobRegistry` ว่ามีงานที่ requestId ตรงกับ entry ในคิวกำลังวิ่งอยู่ไหม — เขียนแล้วอาการยังเหมือนเดิม
**และยังไม่รู้ว่าทำไม**

**รอบหน้าเริ่มด้วยการวัด ไม่ใช่การแก้:** ใส่ log ชั่วคราวดูว่า `jobStarted` ยิงเมื่อไหร่
ตอนนั้น `mEntries` มีอะไร และ requestId ตรงกันจริงหรือไม่ · หนึ่งคำถามหนึ่งการวัด

### ขั้น 1 — ใส่ตัวกลาง (ยังไม่ตัดอะไร)

เปลี่ยนสามตัวแปรเป็นตัวแทนที่อ่าน/เขียนทะลุไปที่ `JobQueue`:

```cpp
struct QueueRunningFlag {
  operator bool() const { return JobQueue::instance().isRunning(); }
  QueueRunningFlag &operator=(bool on) {
    on ? JobQueue::instance().start() : JobQueue::instance().pause();
    return *this;
  }
};
```

**ทั้ง 118 จุดไม่ต้องแก้เลย** แต่ตั้งแต่วินาทีนั้นมีคิวเดียวในโปรแกรม ไม่ใช่สองคิวที่อาจไม่ตรงกัน

⚠️ `--mQueueCount` จะกลายเป็นคำสั่งที่ไม่มีความหมาย (จำนวนคำนวณจาก `JobQueue` แล้ว)
ทำเป็น no-op พร้อมคอมเมนต์ · การลบแถวจริงเกิดใน `JobQueue::jobFinished()` ซึ่งมี test คุม

**หยุดตรงนี้แล้วให้ผู้ใช้ลองคิวจริงหนึ่งรอบก่อน** — ถ้าผ่าน ที่เหลือคือการลบโค้ดล้วนๆ

### ขั้น 2 — ตัดทีละบล็อก บล็อกละ commit

เรียงจากง่ายไปยาก: 3, 4 → 5, 6 → 2 → 1 → 11 → 7, 9 → 8 → 10, 12

บล็อก 11 คือก้อนที่ได้กำไรมากที่สุด (ลบ ~100 บรรทัด) แต่ทำหลังจากที่ 1–6 ผ่านการใช้งานจริงแล้ว
